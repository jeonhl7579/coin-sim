# 작업 흐름: 기획 → 화면 시안 → 개발 지시서

프로젝트 아이템이 정해진 뒤, 기획부터 개발 착수 직전까지 어떤 프롬프트·스킬을 어떤 순서로 썼는지 정리한 문서다.
다음 프로젝트에서 같은 흐름을 쓸 때 참고한다. 사례는 coin-sim(2026-11-10 ~ 11-18)이다.

- 회고는 세션 기록에서 드러난 사실만 근거로 썼다.

---

## 전체 흐름

| 단계 | 도구 | 입력 | 산출물 | 완료 기준 | 사례 기간 |
|---|---|---|---|---|---|
| 1. 기획 | [planning_prompt.md](planning_prompt.md) | 아이템 개요 문서 (`docs/PROJECT_OVERVIEW.md`) | `docs/` 기획 문서 (REQUIREMENTS, FEATURES, PROCESS, SCREENS, PLAYTEST) | 5단계 모두 "확정" | 11-10 ~ 11-12 |
| 2. 화면 시안 | `/design` 명령 | `docs/SCREENS.md` | `design/wireframes/` 로우파이 HTML (화면별 시안 3개, index.html) | 모든 화면 시안 선택, SCREENS.md에 반영 | 11-17 (약 2시간) |
| 3. 개발 지시서 | [claude_md_architect.md](claude_md_architect.md) | 기획 문서, 시안 | `CLAUDE.md`, `docs/development/` | 6단계 승인, 기획 문서 수정 반영 | 11-18 |
| 4. 셋업 | [setup_prompt.md](setup_prompt.md) | CLAUDE.md, `docs/development/`, OVERVIEW 5~7장 | 저장소 뼈대, 아키텍처 패턴(CLAUDE.md·conventions 반영), CI, Vercel 미리보기 | OVERVIEW 7장 0단계 완료 기준 | — |
| 5. 데이터 파이프라인 | [data_pipeline_prompt.md](data_pipeline_prompt.md) | 셋업 결과, OVERVIEW 3·4장, FEATURES | `docs/development/data-spec.md`, 수집기, `data/raw/`, 통계 JSON v1, 계약 코드(TS 타입, fixtures) | OVERVIEW 7장 1·2단계 완료 기준 (전체 수집은 백그라운드) | — |
| 6. 단계별 개발 | [stage_dev_prompt.md](stage_dev_prompt.md) (`이번 단계: N`으로 단계마다 다시 씀) | 통계 JSON v1, `docs/development/progress.md` | 엔진, 검증 리포트, 게임, 화면, 배포 | OVERVIEW 7장 3~8단계 완료 기준 | — |

```
기획 ──→ 화면 시안 ──→ 개발 지시서 ──→ 셋업·구현
  ▲          │              │
  └──────────┴──────────────┘
   뒤 단계에서 앞 단계 기획 문서를 고침 (아래 "되돌아간 지점")
```

### 모든 단계에 공통으로 쓴 방식
- 한 번에 한 단계만 진행하고, 승인("확정", "진행해")을 받으면 다음 단계로 넘어간다.
- 결정할 것은 선택지와 추천안을 함께 받아서 고른다.
- 단계 하나가 끝나면 그 단계에서 쓴 프롬프트를 회고하고 고친다.
- 기획 문서를 고치면 문서 끝의 변경 이력에 한 줄을 남긴다.

### 되돌아간 지점 (뒤 단계에서 앞 단계 문서를 고침)

| 날짜 | 발견한 단계 | 고친 내용 | 계기 |
|---|---|---|---|
| 11-17 | 화면 시안 | 현실감 검증 화면(S-07)을 빼고 개발용 리포트로 전환. 문서 5개 수정 | 시안을 보고 나서야 "시뮬레이터 게임에 굳이 필요한가"가 보임 |
| 11-17 | 화면 시안 | 고른 시안(배치, 연출, 문구)을 SCREENS.md에 반영 | 시안을 확정했으니 기준 문서를 맞춰야 함 |
| 11-18 | 개발 지시서 | 뒤로 가기 처리, 금액 반올림, 지정가 수수료 묶기, 기술 스택, 폴더 구조 | 구현 수준에서 보니 기획에 없던 규칙이 드러남 |

→ 단계마다 "앞 단계 문서 수정" 시간을 미리 잡아 둔다. 시안과 설계는 기획의 빈칸을 찾아내는 단계이기도 하다.

## 1. 기획: planning_prompt.md

**진행 방식**
- 시니어 PM 역할로 5단계를 진행한다: 개요 → 요구사항 → 기능 정의 → 프로세스 → 화면 기획.
- 단계마다 결정 질문을 3개 이내로 받고, 추천안을 가정한 초안을 같이 받는다.
- "확정"하면 `docs/`에 저장한다.

**잘된 점**
- ID 체계(FR, NFR, F, P, S)를 정해 두어서 뒤 단계에서 서로 참조하기 쉬웠다.
- `[추측]`, `[임시값]`, `[테스트 후 결정]` 표시와 PLAYTEST.md 덕분에, 확정한 값과 나중에 정할 값이 문서 안에서 구분됐다.
- 기준 문서를 하나 정하고 다른 문서에는 요약과 링크를 두는 방식으로 중복을 관리했다. 개발 지시서 단계에서 CLAUDE.md의 "문서 지도"를 만드는 근거가 됐다.

**문제와 조치** (11-12 회고에서 나온 내용. 이미 프롬프트에 반영함)

| 문제 | 조치 |
|---|---|
| 첫 응답이 프롬프트 형식을 따르지 않아 1단계부터 다시 시작했다 | 프롬프트의 `[내 아이디어]` 칸에 참고할 문서 경로를 적게 함 |
| 질문 → 답 → 초안 → 확정 순서라 단계마다 최소 2번 오갔다 | 질문할 때 추천안을 가정한 초안을 같이 보여주게 함 |
| "질문 3개 이내"를 맞추려고 여러 결정을 하나로 묶었고, 초안 속 작은 결정이 계속 늘어났다 | 작은 결정은 초안 안에 (제안)으로 표시하고 확정할 때 함께 승인받게 함 |
| 게임 규칙(체결 가격, 등급)을 정할 자리가 없어서 기능 정의 단계로 밀려 들어왔다 | 3단계에 "기능별 규칙"(계산식, 조건, 수치) 절을 추가함 |
| 출력 형식이 모자라 그때그때 열을 추가했다 (NFR ID, 범위, 흐름 ID, 디자인 방향) | 출력 형식 표에 해당 열을 추가함 |
| 저장 규칙이 없어 저장할 때마다 따로 요청해야 했다 | "확정 = docs/에 저장 + 앞 단계 문서 반영"으로 정의함 |
| 데이터 파이프라인처럼 화면이 없는 흐름은 거의 기획되지 않았다 | 흐름 목록에 시스템·개발자 흐름도 넣게 함 |

**아직 남은 개선점**
- 데이터 파이프라인의 세부(통계 JSON 스키마, 수집 명세)는 여전히 기획 문서에 없다. 개발 지시서 단계에서 "시범 수집 → 스키마 확정" 순서로 넘겼다.
- 화면 기획(5단계)은 정적인 배치 위주라, 결과 화면 연출처럼 시간에 따라 움직이는 동작은 시안 단계에서야 정해졌다.

## 2. 화면 시안: `/design`

**사용한 요청**
```
/design docs/SCREENS.md 파일을 읽고 design/wireframes/에 화면별 로우파이 와이어 프레임 시안을 2~3개씩 만들어줘.
HTML 파일이면 좋을거 같아
```

**진행 방식**
- 시작 전에 3가지를 정했다.
  - 결과물: 로컬 HTML만
  - 색: 회색조 (상승·하락만 옅은 빨강·파랑과 ▲▼)
  - 범위: MVP 9개 화면
- 화면을 4묶음으로 나눠 만들고, 묶음마다 멈추고 시안을 골랐다.
  - 1묶음: 공통 CSS, index.html, S-04 게임 (가장 복잡한 화면으로 톤을 먼저 맞춤)
  - 2묶음: S-04a 이벤트 모달, S-04b 그만두기 확인 창
  - 3묶음: S-01 모바일 안내, S-02 메인, S-03 로딩
  - 4묶음: S-05 결과, S-06 기록 목록, S-07 현실감 검증
- 화면마다 시안 A·B·C를 한 파일에 세로로 놓았다. 상태별 변형(준비, 일시정지, 접힌 띠 등)은 작은 박스로 함께 그렸다.
- 각 묶음이 끝나면 헤드리스 Chrome 스크린샷으로 렌더링을 확인했다.
- 모든 시안을 고른 뒤 SCREENS.md에 반영하고 마무리했다.

**선택 결과**

| 화면 | 선택 | 비고 |
|---|---|---|
| S-01 모바일 안내 | A | |
| S-02 메인 | A | |
| S-03 로딩 | C | |
| S-04 게임 | C (가로 티커) | 이후 화면들의 배경 기준이 됨 |
| S-04a 이벤트 모달 | B (오른쪽 사이드 시트) | |
| S-04b 그만두기 | C → **A** | C와 S-04a B를 함께 쓰면 팝오버가 시트를 가린다는 문제를 AI가 지적. 사용자가 A로 바꿔 해결함 |
| S-05 결과 | A → A-1·A-2·A-3 재작성 → **A-2** | 연출 순서(그래프 재생 → 카드 → 등급)를 정한 뒤 A 기준으로 2차 시안을 다시 받음 |
| S-06 기록 목록 | C | |
| S-07 현실감 검증 | 제외 | 기획 변경 (위 "되돌아간 지점") |

**잘된 점**
- 묶음 단위로 멈춰서 먼저 고른 시안(S-04 C)을 다음 화면의 배경으로 썼다. 덕분에 시안끼리 맞지 않는 일이 줄었다.
- 스크린샷 검증으로 렌더링 문제 4건을 사용자가 보기 전에 잡았다: 그리드 위치 바뀜, 칸 높이 0, 메모가 글자를 가림, 그래프 끝점이 수익률과 맞지 않음.
- 고른 시안들을 합쳤을 때 생기는 충돌을 AI가 먼저 짚었다 (S-04a와 S-04b).
- 시안 예시 숫자를 기획 문서의 등급 기준과 대조해 틀린 값을 고쳤다.
- 시안을 보고 나서 기획 자체(S-07)를 다시 판단할 수 있었다.

**개선할 점**
- `/design`은 claude.ai의 Design 캔버스 아티팩트를 만드는 명령이다. 이번처럼 로컬 HTML을 원하면 시작할 때 결과물 위치를 따로 정해야 했다. 요청할 때 결과물 형식을 명시한다.
- 색, 범위, 시안 개수, 묶음 순서를 처음 요청에 넣으면 시작 전 질문을 줄일 수 있다.
- 시간에 따라 움직이는 연출(S-05)은 1차 시안에서 다루지 못해 2차를 다시 만들었다. 연출이 있는 화면은 요청할 때 "연출 순서도 시안에 포함"을 적는다.
- 시안을 고른 이유는 대화에만 남았다. index.html에 선택 이유를 한 줄씩 남기면 나중에 근거를 찾기 쉽다.

**다음에 쓸 요청 예시**
```
/design docs/SCREENS.md를 읽고 design/wireframes/에 로컬 HTML 로우파이 와이어프레임을 만들어줘.
- 화면별 시안 3개, 회색조(상승·하락만 색), MVP 화면만
- 가장 복잡한 화면부터 묶음으로 나눠 진행하고, 묶음마다 멈춰서 내가 고르게 해줘
- 고른 시안은 다음 화면의 배경으로 쓰고, 선택끼리 충돌하면 알려줘
- 연출이 있는 화면은 연출 순서도 그려줘
- 선택한 시안과 이유를 index.html에 표시하고, 다 고르면 SCREENS.md에 반영해줘
```

## 3. 개발 지시서: claude_md_architect.md

**진행 방식**
- 테크 리드 역할로 6단계를 진행했다: 문서 이해 → 설계 → 구현 계획 → 개발 규칙 → 품질 기준 → 초안·저장.
- 중요한 결정은 대안 2개를 표로 비교하고 추천을 받았다.

**잘된 점**
- 대안 비교표가 있어서 추천을 뒤집기 쉬웠다. 통계 JSON 전달 방식과 화면 전환 방식, 2개를 사용자가 뒤집었다.
- 사용자가 낸 안을 다듬어 채택했다 (브랜치 `main ← qa ← dev/*`). 이 과정에서 `dev` 브랜치를 만들면 `dev/...` 브랜치와 충돌한다는 점도 같이 걸러졌다.
- 기획에 없던 규칙을 찾아냈다: 반올림 방향, 뒤로 가기 처리, 지정가 수수료 묶기.
- 규칙을 문서뿐 아니라 도구로도 강제하는 방향으로 정리했다 (ESLint, CI, `.claude/settings.json`).

**문제와 조치** (이미 프롬프트에 반영함)

| 문제 | 조치 |
|---|---|
| 입력 목록에 PLAYTEST.md와 와이어프레임이 빠져 있었다 | 입력을 `docs/` 전체와 `design/wireframes/`로 바꿈 |
| 비밀 정보(.env) 관리를 사용자가 직접 물어서야 다뤘다 | 5단계 항목에 추가함 |
| 분리 문서 위치가 정해지지 않아 나중에 `docs/development/`로 옮겼다 | 위치를 명시함 |
| 기획 문서와 충돌하는 결정을 처리할 규칙이 없었다 | "기획 문서 수정 목록"에 모았다가 6단계 이후 승인받고 반영하게 함 |
| 결정 근거가 대화에만 남았다 | `docs/development/decisions.md`에 기록하게 함 |
| 셋업 전이라 명령어를 검증할 수 없었다 | "예정" 표시와, 셋업 후 다시 맞추는 7단계를 추가함 |
