# Coin Sim — 데이터 명세

게임으로 들어가는 데이터의 계약이다. 수집기(`scripts/collect.ts`)와 통계 추출(`analysis/`)은 이 명세를 채우고, 엔진(`src/engine`)은 이 명세대로 읽는다.

- 작성일: 2026-11-26
- 상태: **초안** (2번 작업 3단계). 시범 수집과 통계 결과를 본 뒤 2번 작업 7단계에서 v1로 확정한다
- 관련 문서: [PROJECT_OVERVIEW.md](../PROJECT_OVERVIEW.md) 3·4장, [FEATURES.md](../FEATURES.md) F-01~11, [conventions.md](conventions.md) 9장, [decisions.md](decisions.md) D-55~D-63
- 표기: **[추측]**, **[임시값]**, **[테스트 후 결정]**은 기획 문서와 같다. **[분석 후 결정]** = 2번 작업 6단계(통계 추출)에서 데이터를 보고 정한다
- 범위 밖: GameWorld와 localStorage 기록 형식은 3번 작업이 이 문서에 장을 추가한다

## 1. 데이터 흐름과 보관 층

```
[업비트 시세 API] → collect.ts → ① data/raw/ → analysis/ → ② data/interim/ → ③ data/stats/stats.json → loadStats() → [게임]
                                                                          ↘ ④ 실제 코인 이름 해시 (③ 안에 포함)
```

| 층 | 내용 | 위치 | git | 밖으로 나가는지 |
|---|---|---|---|---|
| ① 원본 | 업비트 캔들 그대로 (마켓 코드, 시각, 가격, 거래량) | `data/raw/` | 제외 | 나가지 않음 |
| ② 중간 산출물 | 정제한 시계열, 코인별 통계, 실제 코인 이름 원문처럼 실제 코인을 알아볼 수 있는 값. 형식은 계약이 아니며 언제든 지우고 다시 만들 수 있다 | `data/interim/` | 제외 | 나가지 않음 |
| ③ 게임용 통계 | 4장 가공 기준을 통과한 값만 | `data/stats/stats.json` | 커밋 | **배포하면 공개됨** (브라우저가 내려받음) |
| ④ 실제 코인 이름 | 정규화한 해시 목록 (5장) | ③ 안의 `realNames` | 커밋 | 공개됨 (해시만) |

- 브라우저로 가는 파일은 저장소 공개 여부와 관계없이 누구나 받을 수 있다. 그래서 공개 범위는 ③의 **가공 기준**이 정한다 (D-56).
- 통계 자체를 숨기려면 서버에서 시세를 만들어야 한다. 프로젝트를 마친 뒤 업데이트에서 검토한다 (progress.md 후속 작업).
- 상장 폐지된 코인은 다시 받을 수 없다(부록 A). 전체 수집이 끝나면 ①을 저장소 밖에 백업한다.

### 2.2 파일 배치

```
data/raw/
├─ markets.json              # 마지막 실행 때 받은 원화 마켓 목록 스냅샷
├─ state.json                # 수집 상태 (2.5)
├─ candles/1h/KRW-BTC.csv    # 코인당 파일 1개 (2.4)
└─ reports/gaps.json         # 빈 구간 보고서 (2.6)
```

### 2.3 마켓 목록 (`markets.json`)

```json
{
  "fetchedAt": "2026-11-26T04:12:00Z",
  "markets": [
    { "market": "KRW-BTC", "koreanName": "비트코인", "englishName": "Bitcoin", "warning": false }
  ]
}
```

- `markets`는 `market` 오름차순이다. `warning`은 업비트 `market_event.warning`(유의 종목)이다.
- 이번 실행의 수집 대상은 이 목록이다. 목록에서 빠진 마켓(상장 폐지)의 CSV는 지우지 않고 더 받지 않는다.

### 2.4 캔들 CSV (`candles/1h/<market>.csv`)

| 컬럼 | 뜻 | 단위 | 업비트 필드 |
|---|---|---|---|
| `time` | 캔들 시작 시각 (UTC, ISO 8601, `Z` 붙임. 예: `2017-09-25T03:00:00Z`) | — | `candle_date_time_utc` |
| `open` | 시가 | 원 | `opening_price` |
| `high` | 고가 | 원 | `high_price` |
| `low` | 저가 | 원 | `low_price` |
| `close` | 종가 | 원 | `trade_price` |
| `volume` | 거래량 | 코인 개수 | `candle_acc_trade_volume` |
| `quote_volume` | 거래대금 | 원 | `candle_acc_trade_price` |

- 컬럼 순서와 이름은 conventions 9장의 표준 컬럼이다. 출처가 바뀌어도 유지한다 (D-10).
- UTF-8, 줄바꿈 LF, 첫 줄은 헤더다. 숫자는 받은 값을 반올림하지 않고 쓴다.
- `time` 오름차순이고 같은 `time`은 한 번만 있다.
- **끝난 캔들만** 저장한다. `time + 1시간`이 요청 시각보다 늦은 캔들(진행 중인 캔들)은 버린다.
- 체결이 없던 시간은 행이 없다. 채우지 않고 그대로 두며, 정제 단계에서 처리한다 (F-02).

### 2.5 수집 상태 (`state.json`)와 이어 받기

받은 범위는 **CSV를 기준으로** 첫 행과 마지막 행의 `time`에서 읽는다. `state.json`에는 CSV로 알 수 없는 것만 둔다 (D-59).

```json
{
  "markets": {
    "KRW-BTC": { "reachedStart": true }
  },
  "lastRun": { "startedAt": "…", "finishedAt": "…", "status": "ok", "requests": 1234, "failedMarkets": [] }
}
```

| 필드 | 뜻 |
|---|---|
| `markets.<market>.reachedStart` | 상장 후 첫 캔들까지 과거 방향으로 다 받았는지. 응답이 200개보다 적으면 `true` |
| `lastRun.status` | `running`(실행 중. 끝난 뒤에도 남아 있으면 중간에 끊긴 것) / `ok`(전부 성공) / `partial`(일부 마켓 실패) / `failed`(418 차단으로 중단) |
| `lastRun.finishedAt` | 끝난 시각. 실행 중이면 `null` |
| `lastRun.failedMarkets` | 실패한 마켓 코드. 다음 실행 때 다시 시도한다 |

- 마켓 하나를 다 받을 때마다 CSV와 `state.json`을 저장한다. 끊기면 그 마켓에서 받던 것만 잃는다.
- 기존 CSV의 헤더·시각 형식·숫자·순서·중복 중 하나라도 틀리면 그 마켓을 실패로 두고 파일을 덮어쓰지 않는다.
- 같은 `time`인데 값이 다른 캔들은 기존 값을 유지하고 개수를 로그에 남긴다.

이어 받기 순서 (마켓마다):
1. **새 캔들:** `to` 없이 최신부터 과거 방향으로 받다가 CSV의 마지막 `time`에 닿으면 멈춘다.
2. **과거:** `reachedStart`가 아니면 CSV의 첫 `time`을 `to`로 주고 과거 방향으로 받는다. `to`는 그 시각을 포함하지 않으므로 겹치지 않는다.
3. 받은 행을 CSV 행과 합치고, `time`으로 중복을 제거해 정렬한다. 같은 `time`이 이미 있으면 기존 행을 유지한다 (끝난 캔들은 바뀌지 않음).
4. CSV와 `state.json`은 임시 파일에 쓴 뒤 이름을 바꾸는 방식으로 저장한다. 중간에 끊겨도 파일이 깨지지 않는다.

### 2.6 빈 구간 보고서 (`reports/gaps.json`)

정제 단계(F-02)의 필터 근거로 쓴다. 수집 실행이 끝날 때마다(`--markets`로 일부만 받았을 때도) `candles/1h/`의 **모든 CSV**에서 새로 만든다. 실행 시각을 넣지 않으므로 원본이 같으면 보고서도 같다.

| 필드 | 뜻 |
|---|---|
| `summary` | 마켓 수, 전체 캔들 수, 전체 빈 시간 수, 읽기 오류 수 |
| `markets[]` | 마켓 오름차순. CSV가 깨져 있으면 `{ market, error }` |
| `first`, `last` | 첫·마지막 캔들 시각 |
| `expectedHours` | `first`~`last` 시간 수 (양 끝 포함) |
| `presentHours`, `missingHours`, `missingRatio` | 있는 캔들 수, 빠진 시간 수, 빠진 비율(소수 4자리) |
| `gapCount`, `longestGapHours` | 빈 구간 수, 가장 긴 빈 구간(시간) |
| `longestGaps` | 가장 긴 빈 구간 10개 `{ from: 비어 있는 첫 시각, hours }` |
| `inMarketList` | 지금 원화 마켓 목록에 있는지 (없으면 상장 폐지 등) |
| `staleHours` | 모든 마켓 중 가장 최근 캔들 시각 − 이 마켓의 마지막 캔들 시각. 끝부분이 빈 코인(거래 정지 등)을 찾는다 |

- 거래소 전체가 멈춘 시간(여러 마켓이 같은 시간에 빔)은 이 보고서에서 판단하지 않고, 정제 단계에서 원본으로 확인한다.

### 2.7 수집기 동작 계약

| 항목 | 규칙 |
|---|---|
| 실행 | `npm run collect` (전체 원화 마켓). `npm run collect -- --markets KRW-BTC,KRW-ETH`로 일부만 받는다 (시범 수집). `--markets-only`는 마켓 목록만 받고 끝낸다. 목록에 없는 마켓 코드나 모르는 옵션이 있으면 종료 코드 1 |
| 대화형 입력 | 없음 |
| 다시 실행 | 몇 번을 실행해도 같은 원본이 된다. 이미 받은 구간은 다시 받지 않는다 |
| 429 | 다음 초까지 기다렸다가 다시 시도한다 |
| 418 | 즉시 멈추고 실패로 끝낸다. 나중에 다시 실행하면 이어 받는다 |
| 종료 코드 | 0 = 전부 성공 / 1 = 일부 또는 전체 실패 (`state.json`의 `lastRun`에 이유) |
| 로그 | 마켓별 진행과 요청 수만 남긴다. 요청 헤더와 키는 남기지 않는다 |
| 임시 파일 | 시작할 때 `data/raw/` 아래에 끊긴 실행이 남긴 `*.tmp-<pid>`를 지운다 |
| 동시 실행 | 수집기를 동시에 두 개 실행하지 않는다 (임시 파일 정리와 상태 파일이 겹친다) |

## 3. 중간 산출물 (`data/interim/`)

- 분석이 만드는 캐시와 중간 결과(정제한 시계열, 코인별 통계, 성격 분류 결과, 실제 코인 이름 원문)를 둔다.
- 형식은 계약이 아니다. `analysis/` 안에서만 읽고 쓰며, 지워도 원본에서 다시 만들 수 있어야 한다.
- 실제 코인을 알아볼 수 있는 값은 이 폴더 밖으로 내보내지 않는다.

### 3.1 정제 규칙 (F-02, `analysis/clean.py`)

통계에 쓸 1시간 수익률을 만들고, 기준에 맞지 않는 코인을 뺀다. 값을 만들어 채우지 않는다 (D-64).

| 순서 | 규칙 | 값 | 제외 이유 키 |
|---|---|---|---|
| 0 | 업비트 정식 서비스 시작(2017-10-24 00:00 KST) 전 캔들은 버린다 | `2017-10-23T15:00:00Z` | — |
| 1 | 형식 오류: 가격 0 이하, 고가 < 저가, 시가·종가가 고가·저가 범위 밖 | — | `invalidFormat` |
| 2 | 최소 기간: 1시간 수익률 수 | 4,380 이상 (6개월) | `minPeriod` |
| 3 | 스테이블코인: 연환산 변동성 < 30% **이고** 종가 범위(상위 1% ÷ 하위 1%) < 1.5 **[임시값]** | | `stablecoin` |
| 4 | 최소 거래대금: 일(UTC 날짜) 거래대금 합의 중앙값 **[임시값]** | 1억 원 이상 | `minQuoteVolume` |
| 5 | 빈 시간 비율: 첫~마지막 캔들 사이 **[임시값]** | 5% 이하 | `maxMissingRatio` |

- 수익률 = 종가 ÷ 바로 앞 시간 종가 − 1. **바로 앞 시간에 캔들이 있을 때만** 만든다. 빈 시간은 끊김이고, 수익률 조각(4.2)도 끊김을 넘지 않는다.
- 처음 걸린 이유 하나만 남긴다. 큰 급등락은 버리지 않는다 (급등락 통계의 재료).
- 거래소 전체 공백(그 시각에 상장된 마켓이 4개 이상이고 모두 빈 시간)은 세기만 한다.
- `uv run python -m analysis.clean`은 결과를 `data/interim/clean_report.json`(로컬, 실제 이름 포함)에 쓴다. 통계 단계는 정제 결과를 메모리로 받는다.

## 4. 게임용 통계 (`data/stats/stats.json`)

### 4.1 공통 규칙

| 항목 | 규칙 |
|---|---|
| 파일 | 하나. 엔진은 `loadStats()`에서 동적 `import()`로 한 번 불러온다 (D-05, D-60) |
| 크기 | gzip 기준 2MB 이하. 넘으면 내보내기가 실패한다 (NFR-07) |
| 버전 | 최상위 `schemaVersion`(정수). 엔진이 기대하는 값과 다르면 오류 (6장) |
| 키 | camelCase. 상태 키는 `bull`(상승)·`bear`(하락)·`sideways`(횡보) |
| 성격 키 | `leader`(대장)·`large`(대형)·`mid`(중형)·`small`(소형·밈)·`crash`(폭락형) |
| 수익률 | 단순 수익률(비율). `0.01` = +1%. 캔들 1개 = 1시간 |
| 분위수 | `{ "p": [...], "v": [...] }`. `p`는 `meta.quantileGrid`와 같고, 엔진은 사이 값을 선형 보간해 뽑는다. 격자 **[분석 후 결정]** |
| 숫자 | 유효 숫자 자릿수 **[분석 후 결정]** (크기와 재현성) |

### 4.2 구조

엔진에 필요한 값을 거꾸로 뽑은 목록은 부록 B에 있다. 아래 `#`는 부록 B의 번호다.

| 경로 | 뜻 | 단위·범위 | 쓰는 기능 | # |
|---|---|---|---|---|
| `schemaVersion` | 스키마 버전 | 정수 ≥ 1 | F-04 | |
| `meta` | 출처와 분석 조건 (4.4) | | F-04 | |
| `regimes.transition` | 시장 상태 전환 확률. 행 = 지금 상태, 열 = 다음 캔들 상태 (`bull, bear, sideways` 순서) | 3×3, 각 행의 합 1 | F-06 | 1 |
| `regimes.duration.<state>` | 상태 지속 기간 분위수 | 캔들 수 ≥ 1 | F-06 | 2 |
| `regimes.initial` | 시작 상태 확률 | 길이 3, 합 1 | F-06 | 3 |
| `market.volatility.<state>` | 상태별 시장 수익률 표준편차 | ≥ 0 | F-08 | 6 |
| `market.segments.<state>` | 상태별 시장 수익률 조각 (표준화) | 조각 길이 **[분석 후 결정]** | F-07, F-08 | 4 |
| `archetypes.<archetype>.beta` | β 분위수 | 실수 | F-08, F-11 | 7 |
| `archetypes.<archetype>.volatility.<state>` | 고유 움직임 표준편차 | ≥ 0 | F-07 | 6 |
| `archetypes.<archetype>.segments.<state>` | 고유 움직임 조각 (β × 시장을 뺀 나머지, 표준화하고 섞음) | 조각 길이 **[분석 후 결정]** | F-07 | 5 |
| `archetypes.<archetype>.shock.relativeFrequency` | 충격이 처음 발생할 코인을 고르는 가중치 | ≥ 0 | F-11 | 11 |
| `archetypes.<archetype>.shock.up`, `.down` | 방향별 충격 크기 분위수 | 비율 | F-11 | 12 |
| `archetypes.<archetype>.intraCandle` | 캔들 안 움직임 크기 ((고가−저가) ÷ \|종가−시가\|) 분위수. 넣을지 **[분석 후 결정]** | ≥ 1 | F-10 | 20 |
| `marketShock.up`, `.down` | 시장 전체 이벤트 충격 크기 분위수 | 비율 | F-11 | 13 |
| `propagation` | 전파 확률(충격 발생 코인의 성격별), 세기, 범위, 시점, 영향 없음·반대 방향 확률 | **[분석 후 결정]** | F-11 | 14~18 |
| `realNames` | 실제 코인 이름·티커 해시 (5장) | | F-09, NFR-12 | |

- `crash`(폭락형) 값의 출처는 **[분석 후 결정]**이다. 상장 폐지 코인을 받을 수 없어 생존 코인의 폭락 구간이나 임시값을 쓴다 (#10).
- 성격 분류 기준(#9)은 분석 쪽에서만 쓰고, 그 기준값은 `meta.analysisParams`에 남긴다.
- 데이터로 구하지 못한 값은 통계에 넣지 않고 `src/config`의 **[임시값]**으로 둔다. 어느 값이 그렇게 될지는 6단계에서 정하고, v1에서 구조를 고정한다.

**통계에 넣지 않는 것**

| 값 | 둘 곳 | 이유 |
|---|---|---|
| 코인 간 상관관계 | 현실감 검증 리포트가 로컬 원본에서 계산 | 엔진 공식에 쓰이지 않는다 (β로 결과에 반영) |
| 이벤트 횟수·최소 간격 (F-12), 폭락형 등장 확률·대체 자리 (PT-14) | `src/config` | 게임 설정값 |
| 이벤트 종류별 전파 가중치 (#19) | `src/config` **[임시값]** | 데이터에 이벤트 종류 정보가 없다 |
| 시작 가격, 거래량 기준값·비례 계수 (#21·22) | `src/config` **[임시값]** | 가격 수준 정보를 내보내지 않는다 (D-63) |
| 섹터 흐름 (#8) | 없음 (엔진 공식에 0) | 2차로 미룸 |

### 4.3 가공 기준 (D-56)

`stats.json`에는 아래 기준을 통과한 값만 넣는다. 내보내기 스크립트가 검사하고, 하나라도 어기면 실패한다.

| # | 기준 | 검사 |
|---|---|---|
| 1 | 4.2에 정의한 키만 있다 | 허용 키 목록과 비교 |
| 2 | 마켓 코드, 티커, 코인 이름 문자열이 없다. 문자열 값은 정해진 열거값과 `meta.source`뿐이다 | 문자열 값을 모두 꺼내 ② 층의 실제 이름 원문과 대조 |
| 3 | 시각은 `meta.dataFrom`, `meta.dataUntil`에만 있다 | 날짜 형식 문자열 검사 |
| 4 | 가격·거래량·거래대금의 절대값이 없다. 수익률, 비율, 확률, 캔들 수만 있다 | 키별 단위 정의로 확인 |
| 5 | 코인 하나의 값이 없다. 값은 성격 그룹 단위이고, 그룹마다 코인이 최소 N개 이상이다. N은 **[분석 후 결정]** | 그룹별 코인 수를 `meta`에 남기고 검사 |
| 6 | 수익률 조각은 변동성으로 나눠 표준화하고(상태별 평균 흐름은 남김), 여러 코인의 조각을 섞은 묶음으로만 넣는다. 섞기는 고정 시드로 한다 | 조각 묶음마다 출처 코인 수가 N개 이상 |
| 7 | gzip 기준 2MB 이하 | 크기를 출력하고 초과하면 실패 |

- 이 기준이 업비트 약관상 충분한지는 사용자가 판단한다 (부록 A).
- 현실감 검증 리포트(4단계, README 게시)도 같은 기준을 따라 성격 그룹 단위로만 싣는다.

### 4.4 메타데이터와 재현성

```json
{
  "schemaVersion": 1,
  "meta": {
    "source": "upbit-krw-1h",
    "dataFrom": "2017-09-25T03:00:00Z",
    "dataUntil": "2026-11-26T03:00:00Z",
    "markets": { "collected": 301, "used": 0, "excluded": { "invalidFormat": 0, "minPeriod": 0, "stablecoin": 0, "minQuoteVolume": 0, "maxMissingRatio": 0 } },
    "archetypeCounts": { "leader": 0, "large": 0, "mid": 0, "small": 0, "crash": 0 },
    "quantileGrid": [],
    "analysisParams": {}
  }
}
```

- 같은 원본 + 같은 `uv.lock` + 같은 `analysisParams`면 **바이트 단위로 같은** `stats.json`이 나와야 한다.
- 그래서 실행 시각(`generatedAt`)을 넣지 않고, 원본에서 정해지는 시각(`dataFrom`, `dataUntil` = 사용한 원본의 첫·마지막 캔들)을 넣는다 (D-62). conventions 9장의 "생성 시각"은 이것으로 바꾼다 (기획 문서 수정 목록).
- 키는 정렬해서 쓰고, 숫자 형식과 섞기 시드를 고정한다.
- `markets.excluded`의 키와 기준은 3.1 정제 규칙이다. 기준값은 `analysisParams`에 넣는다.

## 5. 실제 코인 이름 (NFR-12) — 엔진과의 계약

가상 코인의 이름·티커가 수집한 실제 마켓과 겹치지 않게 한다. 읽을 수 있는 목록은 저장소에 두지 않고 해시만 둔다 (D-61).

```json
"realNames": { "normalize": "nfkc-lower-alnum", "hash": "fnv1a32", "values": [123456789] }
```

| 항목 | 규칙 |
|---|---|
| 대상 | 수집한 원화 마켓마다 티커(`KRW-BTC` → `BTC`), 한글 이름, 영문 이름 |
| 정규화 `nfkc-lower-alnum` | 유니코드 NFKC → 소문자 → 글자(한글 포함)와 숫자만 남김 |
| 해시 `fnv1a32` | 정규화한 문자열의 UTF-8 바이트에 FNV-1a 32비트. 부호 없는 정수 |
| `values` | 중복을 없애고 오름차순 정렬 |
| 엔진의 의무 | 가상 코인의 티커와 이름(표시하는 모든 언어)을 같은 방식으로 정규화·해시하고, `values`에 있으면 그 후보를 버리고 다시 만든다 |
| 테스트 | `analysis`: 같은 입력에서 Python과 TS의 해시가 같은지 고정 예시로 검사. `engine`: fixtures의 해시 목록으로 거르는지 검사 |

- 해시는 쉽게 거꾸로 찾을 수 있다(짧은 티커). 목적은 비밀 유지가 아니라 **읽을 수 있는 목록을 저장소에 두지 않는 것**이다.
- 해시가 겹쳐서 실제와 다른 이름이 버려지는 일은 다시 만들면 되므로 문제가 없다.
